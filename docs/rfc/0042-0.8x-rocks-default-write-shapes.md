# RFC-0042: 0.8× RocksDB **default** nas shapes de escrita (`_mc4`) e o teto honesto das 1c

**Status:** in-progress
**Updated:** 2026-08-18
**Parents:** [0041](0041-2x-rocks-default.md) (floor oficial 2.0 continua), [0037](0037-apply-off-put-and-2x-pedra.md) (janela de catch-up), [AGENTS.md](../../AGENTS.md) (peer oficial)

## Background

- Peer oficial **não muda**: RocksDB default (`WriteOptions.sync=false`,
  `ROCKS_PARITY_SYNC=0`), Pedra com `fdatasync` antes do Ok (G1). Floor
  oficial do produto continua **2.0** (RFC-0041). Este RFC define uma meta
  **intermediária** — **0.8×** — para os grupos que hoje estão em 0.23–0.57.
- Números oficiais mais recentes (mediana 3 runs,
  [rfc0041-p11/head3](../../findings/rfc0041-p11/head3/); peer `sync:false`):

| grupo | shape | ratio | Pedra qps | Rocks qps |
|---|---|---:|---:|---:|
| `_mc4` (gate 0.8) | `ycsb_a_mc4` | 0.522 | 62 707 | 120 069 |
| `_mc4` (gate 0.8) | `ycsb_f_mc4` | 0.479 | 66 811 | 139 365 |
| `_mc4` (gate 0.8) | `deps_cache_overwrite_mc4` | 0.569 | 31 150 | 69 919 |
| leitura+5% escrita | `ycsb_b` | 0.496 | 390 139 | 785 867 |
| leitura+5% escrita | `ycsb_d` | 0.487 | 387 494 | 795 097 |
| 1c escrita | `ycsb_a` | 0.233 | 49 736 | 201 917 |
| 1c escrita | `ycsb_f` | 0.265 | 45 803 | 165 667 |
| 1c escrita | `deps_cache_overwrite` | 0.298 | 28 339 | 95 218 |

- Escrita 1c custa hoje ~40–44 µs/op (fd p50 medido 22–26 µs ⇒ ~13–18 µs
  não-fd). Escrita concorrente (`_mc4`) custa ~128 µs/op — **pior que a
  1c**: a janela de catch-up fixa de 50 µs
  (`CATCHUP_WINDOW_DEFAULT`, `PEDRA_CATCHUP_US`) espera por escritores que
  podem não chegar, e o custo reaparece na latência do cliente síncrono.
- Aritmética dos alvos (mesma run do peer): `ycsb_a_mc4` ≥ 96 k ⇒ escrita
  concorrente ≤ ~83 µs; `ycsb_f_mc4` ≥ 111 k ⇒ ≤ ~71 µs;
  `deps_cache_overwrite_mc4` ≥ 56 k ⇒ ≤ ~71 µs. `ycsb_b`/`ycsb_d` 0.8×
  exige escrita 1c ≈ fd puro (~24 µs) — na navalha.
- **Teto físico (1c):** um `fdatasync` por Ok serializa em `1/t_fd` ≈
  38–45 k qps. 0.8× Rocks nas 1c pede 76–162 k — **acima do teto** com
  cliente sequencial. Essas shapes sobem até o teto e o número vai honeste
  para a status table; 0.8 nelas **não é gate** (ver Out of scope).

## Problems This Solves

- **Problem:** a janela de catch-up fixa (50 µs) pode queimar mais tempo
  do que o fd que ela tenta amortizar (`wait > fd/2` é perda líquida para
  clientes síncronos).
- **Problem:** não há split medido do custo lone-writer de 1 op
  (encode/append/io/publish); o corte de custo não-fd (~13–18 µs) não tem
  dono definido.
- **Problem:** `_mc4` 0.48–0.57 sem mecanismo identificado de chegada a 0.8.

## Proposed Solution

1. **Break-even na janela de catch-up**: o líder espera no máximo
   `min(PEDRA_CATCHUP_US, fd_recente/2)` — política pura testável + EMA da
   duração real do fd medida no próprio commit. `PEDRA_CATCHUP_US=0`
   continua desligando a espera.
2. **Split instrumentado do caminho lone** (start/apply/io/publish) exposto
   por stats do `ConcurrentDb` + example que mede em condições YCSB;
   **cortar o maior custo não-fd** medido.
3. Remesura oficial (16 shapes × 3 runs, peer `sync:false`) antes/depois;
   medianas em finding; status table reflete o medido, sem inventar 0.8.

## Garantias invariáveis

| # | Garantia | Este RFC |
|---|---|---|
| G1 | `fdatasync` antes do Ok (ou do Ok do grupo) | intocada |
| G2 | visibilidade = lookup / range_at | intocada |

## Acceptance Criteria

- **Tests:** novo teste do bound (política pura + integração com Env de fd
  controlado) em `pedradb-core`; existentes
  `group_commit_amortizes_wal_syncs`, `off_lock_group_fsync_is_durable_on_reopen`,
  `large_batch_skips_catchup_and_flush_reopens`,
  `catchup_window_knob_roundtrip_and_latency_mode` verdes **sem edição**;
  adversarial `rocksdb-compat` verde sem edição.
- **Telemetry:** `findings/rfc0042-p0/` (baseline + split) e
  `findings/rfc0042-p2/` (final): `compare_report.json` por run com peer
  `sync:false`, `medians.txt`, README com antes/depois. Gate deste RFC:
  medianas das três `_mc4` ≥ 0.8. O floor oficial 2.0 do RFC-0041 não é
  alterado nem ligado aqui.
- **Documentation:** este doc + status table em sync com os JSONs.
- **Screenshots:** none — backend-only.

## Out of scope

- 0.8 (ou qualquer gate) em `ycsb_a`/`ycsb_f`/`deps_cache_overwrite` 1c:
  teto medido `1/t_fd` ≈ 38–45 k qps vs 76–162 k necessários. Sobem até o
  teto; o número vai para a status table.
- 0.8 como gate em `ycsb_b`/`ycsb_d` (na navalha do fd; medir e registrar).
- Mudar peer (`sync=false`), shapes, G1, floor 2.0 do RFC-0041, ou adicionar
  thread no `pedradb-core`.
- Shapes de leitura (C/E, MVCC, scan) — continuam P2 do RFC-0041.
