## Why the previous cnt died

Previous resource `cnt_d129bee42cbf4eb1951a15c4cfc666a5` (IP 10.0.0.107, disk_mb=20480 elastic):

- elastic-serve PID 32751 stuck **D-state** in `io_wq_put_and_exit` / io_uring cancel, holding exclusive flock on the reclaim lock and `/dev/ublkc6`.
- SIGKILL does not reap it. `UBLK_U_CMD_GET_DEV_INFO` on **dev_id=6** also D-states the caller (`/tmp/ublk_del6`).
- GET_DEV_INFO on **dev_id=8** returns immediately (`state=QUIESCED`, `ublksrv_pid=-1`) — ublk-control is not globally dead; only id 6 is wedged.
- Reconciler start of the old id sat behind that lock: `elastic volume already locked` / `not ready within 15s (socket=false, ublk=false)`.
- Unlinking the lock file + renaming the elastic dir did not start the old id (backoff + 32751 cmdline still names that path). Leftover reclaim then deleted the renamed dir.
