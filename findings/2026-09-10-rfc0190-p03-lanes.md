# RFC-0190 P0.3 — memtable lanes: table read + per-lane write, one publish fence

**Date:** 2026-09-10
**Host:** Darwin DIAG (not cartaz). Linux guest `linux-gate-p149b` unreachable.
**Peer:** RocksDB default `sync=false` (not metered in this finding — see P0.4).

## Mechanism

- `MemTable` tail is `MEM_LANES=8` `RwLock<LaneData>` buckets (`lane_of` =
  FNV-1a of the user key). `MemTable::new()` stays 1-lane (tests / taken /
  imm / fold). The **active** table opens with `with_lanes(8)` at `Db::open`
  and at every flush content-replace.
- `insert_many` is `&self`: pipeline groups hold the table for **reading**
  and serialize only on the touched lane. Flush still takes the table write
  lock, then every lane (ascending index — the only multi-lane order).
- `apply_async_group_shared` / `apply_group_cold` use `mem.read()` +
  `apply_ops_owned(&MemTable, …)`. All inserts still precede the single
  `published_seq` CAS (group max).
- Intra-group: `insert_many` groups by lane then, for ≥16 items on a
  multi-lane table, drains the two halves of the lane array concurrently
  (`thread::scope`; disjoint lanes, no lock-order cycle). Smaller
  batches stay single-threaded. Inter-group overlap is still the
  table-read + lane-write cut.

## Proof (in-repo)

- `rfc0190_insert_many_lanes_matches_serial` — 64 keys, 8-lane parallel
  drain matches 1-lane serial `insert` (values, len, approx bytes).
- `rfc0190_lane_inserts_are_concurrent_and_visible` — 8 threads × 64 keys
  on one `with_lanes(8)` table, every key visible at `u64::MAX`.
- `rfc0190_concurrent_apply_group_is_atomic` — concurrent snapshot reader
  (`lookup` at `visible_sequence`) never sees `0 < n < N` of a 32-op group.
- `rfc0190_publish_fences_all_shards` — post-Ok `get` of 64 keys (spread
  across lanes) all hit.
- `rfc0055_pipeline_four_writers_async_visible` /
  `rfc0055_writethread_join_eight_writers_visible` green.
- Serial `-p pedradb-core --lib --test-threads=1`: 880 passed / 21 failed /
  4 ignored. Baseline was 874 / 22 / 4. **Zero new failures.** The one
  baseline failure that disappeared (`adaptive_spin_absorbs_slow_leader`)
  is a concurrent-session flake, not claimed as a win of this cut.

## Not in this cut

- Per-member thread fan-out inside one group (leader still `insert_many`s).
- Idx fast-path scan across 8 lanes (8-lane tables take the owned-sort
  merge; 1-lane tables keep the pre-0190 idx cursor). Metered write cells
  do not scan.
- `pedradb-memtable` TCB skiplist — P1.1, gated on cartaz ratio.
