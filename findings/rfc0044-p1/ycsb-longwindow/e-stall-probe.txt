Mechanism (all three verified in code + numbers):
1. Retention: ycsb_a (2M ops, 50% update, zipf theta=0.99 over 1024 keys)
   piles ~140k versions on the hottest key; Pedra auto-compact default keeps
   every version (RFC-0009 F20). RocksDB compaction drops unpinned obsolete
   versions by default.
2. Count walk: Db::count_visible / CountCursor::step_user / SstCountCursor::
   settle walk EVERY MVCC version in the window (by design, RFC-0037
   borrowed-cursor count) — cold scan of the hottest window = 2.3 ms.
3. Amplifier: publish_sequence() -> invalidate_read_answers() clears the
   whole count_cache on EVERY publish (db.rs ~2090: `count_cache.clear()`).
   ycsb_e's 5% inserts (keys >=1024, outside every scanned window) clear it
   every ~19 scans, so nearly all 1.9M scans are cold.

Cross-checks:
- Same 2M-op run with everything memtable-resident (256 MiB, no flush):
  ycsb_e completes at 460k qps (compat-2m-memtable.json) — the cost is the
  SST-resident version walk (settle/block-cache), not the version count
  alone.
- RocksDB same window (64 MiB, rocks-2m.json): ycsb_e degrades 79x from its
  own B/C (1.1-1.3M -> 16.5k qps, 121 s of scans) but completes — its
  compaction GC'd the pile down to few versions/key.
- Pedra product default at 2M: ycsb_e does not complete (>80 min, killed).

Fix axis: ROCKS_PARITY_AUTO_RECLAIM=1 (compat Options.auto_reclaim ->
ConcurrentDb::set_auto_reclaim: pin-aware GC on auto-compact, the Rocks
retention shape). Not the product default; official columns never set it.
Separate possible follow-up (not done): range-aware count-cache
invalidation would kill amplifier 3 without touching retention.
